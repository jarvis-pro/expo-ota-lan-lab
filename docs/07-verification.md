# 07 · 端到端验证（demo.sh）

## 用法

```bash
./demo.sh                # 全流程（含增量构建）
./demo.sh --skip-build   # 复用上次构建，约 40 秒一轮
```

环境变量：`SIM_UDID`（指定模拟器，默认第一台可用 iPhone）、`PORT`（默认 4747）。

## 验证流程

| 阶段 | 动作 | 断言 |
|---|---|---|
| 0 预检 | 校验 app.json 的 IP 与当前局域网一致（不一致自动改写并强制重建）；还原 v1 标记与 v1 资源；启动服务器；全新安装 App | 健康检查通过 |
| 1 基线 | 发布 rollback → 启动 App | 服务器日志出现 `ROLLBACK`/`noUpdateAvailable`；截图为 v1 蓝色且含绿色资源块 |
| 2 热更 | App.tsx 标记改 v2（带时间戳）+ 资源图换橙色变体 → publish → 重启 App | 日志出现新 bundle 与新资源的下载记录；截图为 v2 红色且含橙色资源块 |
| 3 回滚 | publish rollback → 重启 App | 日志出现 `ROLLBACK directive`；截图回到 v1 蓝色与绿色资源块 |

每轮产物存 `artifacts/demo-<时间戳>/`：三张截图 + 完整服务器日志。

## 双重断言设计

1. **服务器日志断言**：证明协议链路真实发生（不是 UI 巧合）。用"标记行号 + 轮询新日志"实现，避免模拟器首次启动慢导致的误判。bundle 和资源（从 metadata.json 解析出文件名）各自等待下载日志。
2. **截图像素采样**：本机 python3 有 Pillow 时，采样屏幕 15% 高度处的中点像素验证 v1 蓝 / v2 红（内容热更），并全图扫描 v1 绿 / v2 橙资源块（资源热更，资源位置随机型变化所以不定点采样）；无 Pillow 自动降级为仅日志断言。

资源热更的机制详见 [08](08-asset-hot-update.md)。

## 可重复性的三个关键

- **每次发布 ID 唯一**：v2 文案内嵌时间戳 → bundle 哈希变化 → 更新 ID 唯一（否则被客户端去重，见 [06](06-troubleshooting.md) 第 6 条）；
- **每轮全新安装**：`simctl uninstall` 清掉客户端更新缓存，保证从内置包起步；
- **基线用 rollback 对齐**：无论服务器 `updates/` 里有什么历史发布，先回滚到内置包再开始。

## 实测结果（2026-11-08）

两次完整运行全部通过：

```
==> [1/4] 基线: v1 内置包        ✅ 服务器响应指令  ✅ 截图为 v1 蓝色 (30,144,255)  ✅ 绿色资源块
==> [2/4] 发布 v2 热更           ✅ 新 bundle 经局域网下载  ✅ 新资源经局域网下载  ✅ 截图为 v2 红色 (230,57,70)  ✅ 橙色资源块
==> [3/4] 回滚到内置包           ✅ rollBackToEmbedded 下发  ✅ 截图回到 v1 蓝色与绿色资源块
🎉 demo 通过
```

首轮曾暴露一个脚本问题：基线阶段服务器正确返回了 `noUpdateAvailable`，但该分支没打日志，导致断言误报失败——修复方式为服务器补日志 + 断言改轮询等待。这也说明日志断言必须以"决策点日志"为准。

历史手工验证的截图见 `artifacts/v1-launch.png`、`v2-running.png`、`v1-rollback.png`。
